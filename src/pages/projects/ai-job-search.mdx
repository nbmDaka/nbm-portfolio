## Problem

Keyword search fails at exactly the moment job search matters most. A candidate who writes "I build backend systems in Go" should surface platform engineering roles — not only postings that literally contain the word "Go". Job descriptions are unstructured, inconsistent, and written by hundreds of different employers; candidate intent is equally unstructured.

The platform needed **semantic retrieval**: match meaning, not tokens, and return ranked results fast enough to feel like search, not like a batch job.

## What was built

The system is a **RAG pipeline** built as a production service, not a demo. Candidate queries and job documents are normalized and embedded into a shared vector space. The **vector database** performs approximate nearest-neighbor retrieval to produce candidate matches; a downstream AI ranking stage assembles context and re-ranks for final recommendations. The retrieval path — embed, query, re-rank — was kept inside an interactive latency budget.

Freshness is designed in: new or updated job postings flow through the embedding pipeline continuously, so the index reflects the live market rather than a nightly snapshot.

## Engineering decisions

### Retrieval before generation

Relevance is won or lost at retrieval. The pipeline invests in clean document normalization — title, responsibilities, requirements, seniority signals — before embedding, because a perfect model cannot recover from noisy input.

### Hybrid ranking

Vector similarity alone optimizes for semantic closeness, not for match quality. Retrieval output is re-ranked by an AI stage that weighs intent fit, seniority alignment, and requirement overlap. The result is a ranking that explains itself.

### Latency budget as a constraint

Interactive search has a hard latency budget. Embedding generation, vector query, and re-ranking were each measured and bounded; anything that could not meet the budget was moved off the synchronous path.

### Evaluation loop

"Relevant" is meaningless without measurement. Relevance was tracked against a versioned evaluation set with graded relevance judgments, and pipeline changes shipped only when measured relevance improved.

## Challenges

**Unstructured, inconsistent source data.** Job postings range from one line to legal documents. Normalization and chunking strategy mattered more than model choice — most early quality gains came from data shaping, not from switching models.

**Embedding drift and index freshness.** As postings changed, stale embeddings silently degraded match quality. Continuous re-embedding with versioned indexes kept retrieval honest.

**Cold-start relevance.** With little behavioral signal, ranking had to lean on content quality. Structured requirement extraction gave the ranker signal that raw text could not.

## Impact

- Semantic search replaced keyword matching across the live job catalog
- **RAG pipeline** in production: continuous embedding, vector search, AI re-ranking
- Relevance improved against a versioned evaluation set
- Retrieval path held an interactive latency budget
